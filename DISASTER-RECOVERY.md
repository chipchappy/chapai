# Disaster recovery — claritynclex.com

**Read the first section before panicking. It is usually the answer.**

## If the laptop dies, the site does not

claritynclex.com is a **Cloudflare Worker already deployed to the edge**, and the
question bank lives in **Cloudflare D1**. Neither runs from the laptop. Losing
the machine costs you the ability to *change* the site, not the site itself.

Verify at any time, from anything with a browser:

```
curl -s -o /dev/null -w "%{http_code}\n" https://claritynclex.com/
```

`200` means you are serving. Recovery below is about restoring your ability to
build and deploy, and about the data that is *not* already on Cloudflare.

## What lives where

| Asset | Where it survives | Recoverable without the laptop? |
|---|---|---|
| Running site | Cloudflare Worker `chapai-web` | Already running |
| Question bank, users, billing | Cloudflare D1 `chapai-prod` | Yes — live, plus R2 dumps |
| Application source | GitHub `chipchappy/chapai` | Yes |
| Untracked content generations | R2 `content/<date>/*.tar.gz` | Yes, since 2026-08-26 |
| `node_modules`, `.next`, `.open-next` | Nowhere — and that is correct | Regenerated by build |
| `dev` commits | GitHub (pushed 2026-08-26) | Yes |

Anything committed only on this machine is the real exposure. See "Standing risks".

## Recover the toolchain on a new machine

Requires Docker and nothing else — no Node, no npm, no local setup.

```
git clone https://github.com/chipchappy/chapai.git
cd chapai
docker build -t chapai .
```

The image build runs `type-check` and the full test suite, so it fails at build
time rather than mid-outage if the toolchain is broken.

Then authenticate and deploy:

```
docker run --rm -it -v "$PWD":/app -w /app chapai npx wrangler login
docker run --rm -it -v "$PWD":/app -w /app --env-file apps/web/.env.production chapai \
  bash -c "npm run -w @chapai/web build:worker && npm run -w @chapai/web deploy"
```

**`build:worker` before `deploy`, always.** `deploy` uploads whatever is already
in `.open-next/` — it does not build. Skipping the build ships a stale worker,
which has cost a wasted deploy before.

## Restore the database

Only if D1 itself is lost or corrupted — not needed for a dead laptop.

```
# newest dump
npx wrangler r2 object get clarityccrn-guild-backups/d1/chapai-prod-<date>.sql \
  --file restore.sql --remote

# sanity-check before touching production
grep -c '^CREATE TABLE' restore.sql   # expect ~37
grep -c '^INSERT INTO'  restore.sql   # expect >15,000

npx wrangler d1 execute chapai-prod --remote --file restore.sql
```

Cloudflare D1 also keeps its own point-in-time history, which is usually a
faster path than a dump restore:

```
npx wrangler d1 time-travel info    chapai-prod
npx wrangler d1 time-travel restore chapai-prod --timestamp <ISO-8601>
```

## Restore content generations

Needed only when re-syncing the bank, never to build or serve.

```
npx wrangler r2 object get clarityccrn-guild-backups/content/<date>/promoted-v5.tar.gz \
  --file promoted-v5.tar.gz --remote
tar -xzf promoted-v5.tar.gz -C packages/content/staging/
```

Available archives: `promoted-v3`, `promoted-v4` (raw generations, 32,746 rows
each, ~92% duplicate stems) and `promoted-v5` (the deduped candidate set,
1,880 questions, what the sync scripts now read).

`promoted-v2` stays in the working tree deliberately. It is the content
pipeline's default input **and** output directory for
`rewrite-distractor-rationales`, `retag-question-types`, `generate-p1-bow-ties`
and `generate-p1-ngn-case-studies` — deleting it on size alone breaks those
scripts' defaults. It is tracked in git, so GitHub is its backup.

## Keeping backups current

```
node scripts/backup-to-r2.mjs            # D1 + untracked content, verified
node scripts/backup-to-r2.mjs --d1-only  # faster, database only
node scripts/backup-to-r2.mjs --dry-run  # show the plan, change nothing
```

Every upload is re-downloaded and SHA-256 compared before it is reported as
success, and the D1 export is rejected if it parses to implausibly few tables or
rows. A backup nobody has read back is a guess.

Run it before any risky content operation, and on a schedule you will actually
keep. Weekly beats "when I remember".

## Standing risks

1. **`dev` is fully pushed as of 2026-08-26.** Keep it that way — anything
   committed only here dies with the machine. Note that pushing `dev` deploys
   to STAGING; only `main` deploys production.
2. **`packages/content/staging/promoted-v5` is untracked** and feeds
   `d1:sync:p1.6:prod:full`. It is in R2 as of 2026-08-26 — keep it that way.
3. **The repo is public.** Treat everything committed as published. Never commit
   `.env*`, cookies, or captured response headers.
