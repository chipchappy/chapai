# Architecture

## Isolation Strategy

The simulator is additive. It shares authentication, hosted user identity, brand components, analytics adapters, and authorized cohort membership with Clarity. It does not share quiz sessions, question records, readiness scores, billing state, or NCLEX progress tables.

## Request Flow

1. `page-access.ts` checks the server feature gate and authentication in the layout and every page before scenario lookup or rendering. The repeated page checks prevent parallel React Server Component rendering from serializing protected child data behind a parent soft-404.
2. Every `/api/clinical-simulation/*` handler independently repeats the feature and identity checks.
3. `ensureHostedUser` maps the authenticated account to the existing D1 user identity.
4. The attempt API loads the attempt with both `attempt_id` and `user_id` predicates.
5. The server applies a structured action or clock advance through the deterministic engine.
6. The server persists the resulting state, action classification, transition metadata, scores, and errors.
7. The browser renders the returned authoritative snapshot.

The browser never submits a score or arbitrary patient state.

## Modules

- `schema.ts`: Zod scenario contract, TypeScript types, structural and referential validation
- `scenarios.ts`: six versioned scenario definitions and evidence metadata
- `future-scenario-outlines.ts`: non-playable planning records only
- `engine.ts`: seeded state creation, effects, conditions, events, time, action classification, scoring, debrief
- `feature.ts`: fail-closed environment and production allowlist gate
- `page-access.ts`: fail-closed page guard applied before protected scenario data is rendered
- `access.ts`: feature, authentication, D1, and hosted-user API guard
- `store.ts`: isolated attempt, action, debrief, and assignment persistence
- `components/clinical-simulation/*`: catalog, prebrief, workstation, monitor, and debrief
- `SimulationDeveloperPanel.tsx`: protected clock/event/state/score/reset/replay/trace testing controls
- `scripts/clinical-simulation-local.mjs`: local-only migration, test-user, inspect, reset, and destroy workflow
- `apps/web/wrangler.clinical-simulation.local.jsonc`: route-free local Worker/D1 configuration

## Determinism

Each attempt stores a 31-bit random seed and scenario version. Controlled initial variation is generated by a deterministic xorshift stream. All later state changes are explicit effects from actions, delayed effects, or scenario events. This allows an attempt to be reproduced for support, clinical review, and test failures.

## Data Model

### `clinical_simulation_attempts`

Owns one student's current snapshot and result. Important fields include user, scenario/version, mode, status, seed, virtual minute, serialized state, serialized domain scores, critical errors, timestamps, and debrief viewed state.

### `clinical_simulation_actions`

Append-only decision record containing attempt/user ownership, action ID, category, classification, virtual minute, structured selections, and state-transition metadata.

### `clinical_simulation_assignments`

Stores cohort, authorized instructor user, scenario, mode, passing-domain target, due date, and creation time. Existing `access_key_grants` remains the source of cohort authorization.

## Authorization

Cloudflare D1 does not provide PostgreSQL-style row-level security. Equivalent isolation is enforced at the API query boundary:

- Student attempt reads and writes include the authenticated hosted user ID.
- Attempt action rows repeat user ownership for auditability.
- Instructor reports first resolve an active instructor cohort, then join only active student grants in that cohort.
- Assignment creation always uses the resolved instructor cohort and hosted instructor user.
- Disabled feature routes return 404 before data access.
- Production page access requires an authenticated allowlisted email at both the page and layout boundaries.

If persistence moves to Supabase PostgreSQL, mirror these rules in database RLS policies and retain API checks as defense in depth.

## Reliability

- State is saved after every action and clock advance.
- Pause, abandon, reset, and replay state changes are server-persisted rather than browser-local.
- Attempt records retain scenario version and seed.
- Completion is server-enforced and cannot occur before the scenario minimum action count.
- No free text controls clinical effects.
- Scenario files have no executable expressions; they are parsed against a closed schema.
- Reversible migration `0007` owns all new database objects.
- Sanitized attempt traces omit identity and authentication data and require developer authorization.

## Privacy

Only account identity, educational actions, simulated state, and competency results are stored. The product does not need or request real patient data. Third-party analytics receive scenario/action IDs and classifications, never communication text or documentation content.
